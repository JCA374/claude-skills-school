Lesson 1

What a skill is

▶ Anatomy of a skill🎧 Episode 1

A skill is a folder containing a file called SKILL.md. The file has two parts:

  1. A YAML header (frontmatter) between --- lines. It must have a name and a description.
  2. A markdown body: the instructions, written like a briefing for a capable colleague who has never seen your project.

Next to it there can be anything the instructions need: scripts/ (code Claude runs), references/ (longer docs Claude reads only when told to), assets/ or template/ (files copied into the output).

ml-project-site/
├── SKILL.md               ← 71 lines: when to use, set-up steps, rules
├── scripts/init.sh        ← copies the template into a project
└── template/              ← publish.py, publish_loop.sh, docs/*.js, style.css …
project-podcast/
├── SKILL.md
├── scripts/prepare.sh, publish.sh, make_feed.py, conf.sh
└── assets/index.html, podcast.conf.example

Look at the sizes on the Your skills page. Your skill files are 52–85 lines each, and the scripts behind them are about 1,400 lines. That's the right shape: short instructions, heavy code. The instructions explain intent and judgment. The code does the repeatable work exactly the same way every time.

Skill vs prompt. A prompt is gone after one chat. A skill is a prompt that is saved, versioned and reused, can ship its own tools, and loads itself when relevant. Each time you write the same instructions to Claude for the third time, that's a skill waiting to be written.
Try it. In any project, ask Claude: "Show me the SKILL.md of project-podcast and explain each section in one line." Then open ~/.claude/skills/project-podcast/ yourself and compare.
Self-check: which two header fields are required?

name and description. Everything else is optional.

Lesson 2

How Claude picks and loads a skill

▶ How Claude picks and loads a skill🎧 Episode 1

This is the most important lesson. Skills use progressive disclosure, which means three levels of loading:

1
Always: at the start of every session Claude gets a list with the name and description of each available skill, and nothing else. This costs roughly 100 words per skill.
2
When chosen: if your request matches a description (or you type /skill-name), Claude calls its Skill tool and the body of SKILL.md is loaded into the conversation.
3
When a step needs it: Claude reads a reference file or runs a script that the body points to. A script's code doesn't need to be read at all. Only its output comes back.

Consequences you can use:

  • You can install many skills. Unused ones cost a line each, not their whole content.
  • The description decides everything. If it doesn't match how you phrase requests, the skill never loads (lesson 4).
  • Claude only reaches for a skill when the task needs one. A one-step request like "read this PDF" may be done directly, even if a PDF skill exists. Multi-step, specialised work is where skills fire reliably.
  • Your CLAUDE.md can point at skills. Yours says "for ML project websites use ml-project-site". That's a strong, cheap hint that tips the choice.
Try it. Start a fresh session and say: "I want a live progress page for my new RL run." Watch for the Skill(ml-project-site) call. Then try a vague version, "make a website", and see whether it still fires.
Self-check: why doesn't a 2,000-line reference file slow down every session?

Because it's level 3: it's only read when a step in SKILL.md says to read it. Until then, only the description (level 1) is in context.

Lesson 4

Writing the description: the trigger

A good description answers two questions: what does it do and when should Claude use it. It should include the words you actually say, plus the near-synonyms. Claude tends to under-use skills, so lean towards being explicit ("use it whenever…, even if they don't say X").

Your best one, annotated

description: Write, voice and deploy a short spoken podcast episode       ← WHAT
  about a project's progress to the project's GitHub Pages site …
  Use it whenever something significant happens in a long-running        ← WHEN (event)
  project (a breakthrough, a stage or goal passed, a new best result …),
  or whenever the user asks for a podcast, an audio update, an episode,  ← WHEN (words)
  a spoken summary of progress, or to publish/deploy an episode,
  even if they don't say "podcast".                                      ← pushes past exact words

A checklist

  • Starts with a verb phrase saying what it produces.
  • "Use when …" lists situations and trigger words.
  • Names the boundaries if a neighbour skill is similar ("not for Word files; use docx"). Anthropic's own skills do this a lot.
  • States inputs and outputs if it's a pipeline stage. Your kokoro-narrate says "Input is …chNN.txt from narration-prep; output is … for audiobook-assemble", so Claude can chain them correctly.
  • Fewer than ~120 words. Yours range from 46 to 119.
Try it. Rewrite the description of failure-analysis-report so it also fires for "why does my model crash in level 3?" or "find better features". Then test both versions with the skill-creator's description optimizer (lesson 7).
Self-check: what's wrong with "description: Helper for websites"?

No "when", no trigger words, no boundaries. Claude can't tell when it applies, so it will rarely be chosen and sometimes chosen wrongly.

Lesson 5

Scripts, references and pipelines

▶ Skills that work together

Put in a script whatever must be done exactly the same way every time: rendering, loudness normalisation, publishing, feed building. Put in the instructions what needs judgment: which voice, whether a phrasing flag is real, what to say in an episode.

References are for long material that's only sometimes needed, such as a checklist per domain. The body should say when to read each one ("for ML papers read references/ml-papers.md").

Pipelines: skills that hand over to skills

Your audio work is split into five single-purpose stages, each with a clear input and output file:

chNN.md ─speech-flow→ chNN.md (fixed for the ear) ─narration-prep→ audio/chNN.txt
        ─kokoro-narrate→ audio/chNN.wav ─listen-check→ chNN.listen.json ─audiobook-assemble→ .mp3 + .m4b

voice-text then gives one launcher (voice.sh new|scan|prep|narrate|listen|export|status) that any project can use. project-podcast builds on voice-text, and ml-project-site builds on project-podcast. Because each layer calls the one below rather than copying it, a fix in the studio improves every podcast.

Verification gates. Your best skills end with a check that proves the job is done: "Deployment counts only when Pages says built <HEAD sha> and the page returns 200"; voice.sh status exits 0 only when all five stages PASS. Without such a gate, "done" means "Claude thinks it's done".
Try it. In any repo: "Use voice-text to turn README.md into an MP3." Follow the stages it runs, and look at voice/<slug>/pipeline.log.jsonl afterwards.
Lesson 6

How a skill learns

▶ How a skill learns🎧 Episode 2

A skill doesn't learn from data on its own. It learns because a lesson gets written into it. A chat is forgotten; a skill file isn't. Your audiobook studio has the best loop on your machine:

1
Report: you say "this sounds wrong", or listen-check flags it and a second Whisper model agrees.
2
Case: training/NN-slug.md plus a .before and an .after script, both rendered to audio.
3
You choose by ear. Taste stays with you.
4
Rule: added to the right skill ("Learned rules" in narration-prep, the check table in speech-flow).
5
Test: a before/after pair in rule-tests.yaml; test_rules.py must pass before publishing, so a new rule can't quietly undo an old fix.

Ten cases so far. Case 01 (a flat "Can I?") became the (+2) + ?? markup that now runs on every book and podcast, including this site's. Case 08 ("I want it on the record" heard as "I wanted on the record") was found by the machine listener, not by you.

It happened while building this site. Podcast episode 2 quoted case 08's line word for word, and Kokoro made exactly the same mistake again: listen-check flagged "want it" heard as "wanted" at 1:36. The rule from case 08 ("avoid want it + vowel in af_heart") applies to every text, including a lesson about the rule. The episode was rephrased and re-rendered; only the changed paragraph had to be voiced again, thanks to the per-paragraph cache.

Your ml-project-site shows the lighter version: a "Rules learned the hard way" section. "Never git pull --rebase --autostash" is there because it once silently reverted an hour of work.

Try it. Next time Claude does something wrong while using a skill, say: "Write this lesson into the skill, with the why, and add a check if it can be detected."
Self-check: why keep the "before" version of a case?

So you can hear (or test) that the rule really made the difference, and re-check old cases when rules change later.

Lesson 7

Measuring a skill (skill-creator)

Anthropic's skill-creator skill (already synced to your machine) turns "it feels better" into a measurement:

  1. Test prompts: 3–5 realistic requests, the kind you would actually type.
  2. Paired runs: each prompt runs with the skill and without it (or with the old version), in parallel subagents.
  3. Assertions + review: objective checks are graded automatically; you look at outputs side by side in a viewer and leave feedback.
  4. Iterate: improve, re-run into iteration-N+1, compare against the previous one.
  5. Description optimisation: ~20 queries that should and should not trigger the skill, including near misses; it measures how often the skill fires and rewrites the description to do better.

This is exactly your failure-analysis-report discipline applied to skills: paired comparison against a baseline, and "findings are leads until validated".

Try it. "Use skill-creator to benchmark project-podcast: three test episodes from the bipedal project, with and without the skill."
Lesson 8

Writing style that works

  • Explain the why. "NEVER X" in capitals gets obeyed but can't be generalised. "Don't X, because Y" lets Claude handle cases you didn't foresee. Your listen-check explains in a whole paragraph, with measurements, why there is no pitch check. Nobody will re-add it by mistake.
  • Keep it lean. Aim for SKILL.md under ~500 lines; move detail into references/ with a clear "read this when…". Remove instructions that make Claude waste time.
  • Point to a reference implementation. "lunarlander-98 is the reference: look there for a complete example of every hook" beats pages of description. Make sure the path is right (see the audit).
  • Bundle repeated work. If Claude writes the same helper script in three sessions, put it in scripts/.
  • Say what "done" means, and how to verify it (lesson 5).
  • Ask-first points. Your ml-project-site says "ask the user before creating a public repo". Write down which actions need your OK.
  • Trust. A skill can make Claude run code. Only install skills from sources you trust, and read the scripts of any skill you download.
